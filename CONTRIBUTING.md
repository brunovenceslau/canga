# Contributing to canga

This page is for anyone changing canga's code or documentation: how to get a
change green locally, what the repository expects of a commit, and which
document a change belongs in. To use canga, start at the
[README](README.md).

- [Report a bug or propose a change](#report-a-bug-or-propose-a-change)
- [Get a change green](#get-a-change-green)
- [Commits](#commits)
- [Where a change is documented](#where-a-change-is-documented)

## Report a bug or propose a change

Open a [GitHub issue](https://github.com/brunovenceslau/canga/issues). Say
which build you ran and which release: `canga --version` prints both, for
example `v0.10.5 (host, <commit>, go1.27.0)`.

## Get a change green

The Go version, `make tools`, `make ci` and every other target are listed
under [Contributing](README.md#contributing) in the README. Run `make ci`
before you push: it is the full local gate.

On a pull request, GitHub Actions runs a subset of those targets, split by
where each build runs: `make test-host` on macOS, `make test-sandbox` and
`make e2e-sandbox` on Linux, plus `make cross`, `make lint` and `make vuln`.
`make test` and `make license-check` run only locally.

Install the commit hook once per clone. On a Mac, with canga itself:

```sh
canga git setup-hooks
```

Anywhere else, including Linux, where the host build is not published:

```sh
git config core.hooksPath .canga/hooks
```

The hook runs `make pre-commit` (`go fix`, the `golangci-lint fmt`
formatters and `go vet`) and refuses the commit if that changed any file,
so you read what the tools rewrote before committing it.
[Commit hook](README.md#commit-hook) explains why it refuses rather than
amending.

A few gates check things a reviewer would otherwise miss:

- **SPDX header.** `make license-check` fails on any tracked file, other
  than `go.sum` and `LICENSE`, without an `SPDX-License-Identifier:` line in
  its first five lines. By convention a file starts with the same two SPDX
  lines this one does, in its own comment syntax.
- **README install blocks.** `readme_install_test.go` runs the README's
  by-hand install blocks, unchanged, against a fake release. Editing one of
  those blocks changes what the test runs; keep them valid POSIX shell that
  is safe to paste into an interactive shell.
- **Command examples.** Every command that does work has an `Example` in
  its help, and a test fails if a new one does not.

## Commits

Match the existing history:

- [Conventional Commits](https://www.conventionalcommits.org/) subjects,
  such as `fix(upgrade): ...` or `docs(readme): ...`.
- Signed commits (`git commit -S`, SSH or GPG).
- Pull requests target `main`.

There is no `CHANGELOG` file. Release notes are generated by GitHub from the
merged pull requests when a release is published (see
[Releasing](docs/releasing.md)), so a pull request's title is what a user
reads in them.

## Where a change is documented

| Document | Holds | Update it when |
| --- | --- | --- |
| [README.md](README.md) | What each command does, install, configuration, exit codes | A command, flag, variable, exit code or install step changes |
| [docs/design.md](docs/design.md) | How each command works, the guarantees it makes and where they stop | The mechanism behind a guarantee changes |
| [docs/migrating.md](docs/migrating.md) | One-time steps for machines and sandboxes on an older setup | A change needs existing users to act |
| [docs/releasing.md](docs/releasing.md) | The maintainer's release runbook | The release path changes |
| [docs/HANDOFF.md](docs/HANDOFF.md) | The maintainer's dated working log and open items | Not for user-facing facts: those go in the pages above |
| Command help (`Short`, `Long`, `Example`) | A short form of the README's facts, at the terminal | The command's behavior changes |

State a fact once and link to it from elsewhere. Every claim about
behavior should be checkable against the code or a command's output, and
text about a security check says exactly what it proves and what it does
not.
